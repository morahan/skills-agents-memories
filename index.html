Skills, agents, and memories

These three words get used like synonyms. They are not. In a modern AI system they sit on different layers of the same stack.

Who

Agent

The hire. A runtime with a goal, tools, and a loop. It decides whether to keep going.

How

Skill

The SOP binder. A playbook loaded on demand for a class of work. It does not clock in.

What

Memory

The scar tissue. What is true, and what already happened, after the context window dies.

01 — Analogy

A new hire on day one.

An agent uses skills and memories. Skills do not run themselves. Memory does not execute. Mix those up and you get a stuffed system prompt that looks sophisticated and behaves like amnesia with extra steps.

Anthropic’s own metaphor for a skill is an onboarding guide, not a second employee. Steal it. It is correct.

The agent is the hire. They have a mandate, a desk, tools, and a loop: look, think, act, check whether the job is done. Without that loop they are just sitting in Slack.

The skill is the SOP binder. “When someone asks for a refund, follow these steps. Use this template. Do not invent policy.” You do not tattoo the binder on their forehead. They pull the right folder when the task shows up. That is progressive disclosure, not magic.

Memory is everything they learned after day one. This customer already got a courtesy credit. This repo uses pnpm. Last deploy died because someone edited the env file by hand.

The model itself is stateless. Every inference starts from zero. Continuity is an engineering layer you add around it.

02 — Definitions

What each one actually is.

Runtime

Agent

A system, not a model. Take a goal. Plan. Call tools. Observe. Decide the next action until the goal is met or a stop condition fires. Simon Willison still has it: an LLM in a loop with tools. The model reasons. The agent does. A chatbot that answers once is not an agent. A script that always calls the same tool in the same order is a workflow.

Playbook

Skill

Packaged procedural knowledge for a class of tasks. The 2026 format is a folder with SKILL.md plus optional scripts and templates — now an open spec at agentskills.io. At startup the agent sees only name and description. The full file loads when the task matches. A skill that is always in the prompt is just a system prompt wearing a costume.

Persistence

Memory

The writable store that survives a single model call. Working memory is the context window. Episodic memory is what happened. Semantic memory is what is true. Procedural memory is how to do things — which is where skills live on paper, and should not live as folklore in a notes file.

They are not alternatives.

04 — Worked example

One ticket. Three layers.

Support / RefundTicket 4821

“Refund this customer.”

Memory

Enterprise plan. One courtesy credit already granted in March.

Skill

Refund playbook: eligibility, approval threshold, tone, which fields to log.

Agent

Pulls the order through a tool, applies the playbook to those remembered facts, then refunds or escalates.

No memory

Amnesiac intern. Re-asks everything. May issue a second courtesy credit.

No skill

Improvises policy. Sometimes generous, sometimes illegal, never consistent.

No agent

A well-written PDF that cannot click Submit.

05 — When to build which

Do not start with a fleet.

Write a skill

When the procedure is known and repeatable — review checklist, refund rules, how we make a deck. You are tired of re-explaining it. You want it versioned in git and loaded only when relevant.

Add memory

When facts, preferences, or events must survive the session, and when the system should write back what it just learned. If it only reads, you built a search index.

Build an agent

When the next action depends on observations. Multi-step work, tools, a stop condition. Skills and memory are what make that loop useful the second time you run it.

06 — Production mistakes

The mix-ups that ship.

  1. Calling a chatbot an agent. One reply is not agency.
  2. Stuffing procedures into memory. “Remember how we deploy” becomes folklore. Put the procedure in a versioned skill.
  3. Stuffing facts into skills. A playbook that hard-codes the user’s name is a diary. Skills should still be right if the user changes.
  4. Treating RAG as memory. RAG is a corpus a human stored. Memory is what this agent wrote back. Different write path. Different trust model.
  5. Treating tools as skills. Hands versus training. MCP gives access. A skill says when to use it and what “done” looks like.
  6. A stuffed system prompt as a fake hybrid. Always-on walls of instructions fight each other and get ignored.
  7. Memory with no forget path. Stale pricing, stale preferences, confident wrongness. Bad memory makes agents worse.
  8. Skills that never fire or always fire. Progressive disclosure lives or dies on the description.
  9. No write-back. Read-only “memory” is search.
  10. One mega-agent instead of composable skills. Hard to test, hard to share, hard to debug.
07 — Adjacent terms

So they do not become a fourth lesson.

Tools / MCP give access. A database connector lets the agent query billing. A skill tells it which query pattern to use and what eligible means. Access is not judgment.

System prompts / AGENTS.md are standing instructions that load every session. Keep them short. If a procedure is only sometimes relevant, it belongs in a skill.

Sub-agents are workers with their own context windows. Use them for isolation. Use a skill when the current agent needs a playbook. A skill is instructions. A sub-agent is a worker.

On paper, skills are externalized procedural memory. In engineering, keep the storage separate: skills are versioned playbooks; memories are accumulated state that can go stale. Related layers. Different lifecycles.

The agent is the employee. The skill is the runbook. Memory is the scar tissue.
